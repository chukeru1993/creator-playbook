# 技术讲解规则

在讲解技术、工程、AI、研究或深度概念时读取本文件，并同时遵守 [通用写作规则](core-writing-rules.md)。目标是让观众理解机制和决策含义，而不是复述表面现象。

## 机制、因果与决策

1. 先说清现象或真实问题，再解释底层机制。
2. 将机制展开成可检查的因果链；每一步说明前因、变化和后果，避免跳步。
3. 多个影响因素并存时，拆成独立变量讨论，避免把相关性混写为单一原因。
4. 每个核心判断后回答“这对实际工程意味着什么”：给出判断标准、设计约束、验证方式或下一步。

不要只说“模型很强”“系统有风险”“某技术改变行业”。说明它如何发生、在什么条件下成立、对谁有什么实际影响。

## 概念对比与术语

- 涉及范式、方案或概念区分时，用一致维度对比，例如工作单元、交互模式、成本、可靠性、适用条件和验证方式。口播可配表格、分屏或逐项高亮。
- 首次出现关键英文术语时，采用“英文原词（中文说明）”；念清英文，并让中文说明解释它在当前论证中的作用。
- 不要用术语替代解释。先给可感知场景或机制，再让术语成为可检索的标签。

## 深度概念的三层展开

概念本身是论证关键而非装饰时，按以下顺序展开：

1. **历史或原始语境**：说明概念从何种真实问题中出现。
2. **当前机制传导**：逐步映射到当前主题，确保每一步都能被材料或推理支撑。
3. **工程后果**：给出具体决策、脆弱点或保护措施，而不是泛泛感叹风险。

不要为了“深度”把每个概念都讲成三层。短视频只保留支撑主结论所需的最短因果链；长视频再分章展开。

## 概念接地

- 用熟悉场景、具体对象、类比或自问自答降低理解门槛，但不得删掉决定结论的技术条件。
- 类比只解释一个关系时，明确它的边界；不要让比喻取代机制。
- 把抽象结论翻译成观众能判断的场景，例如把“审查瓶颈”落到谁在什么环节必须做什么判断。
- 让观众在每个关键句号获得一次可验证的理解，而不是被从句和名词堆叠拖住。

## 收束

以可行动的认知产出结束：应检查什么、如何判断是否适用、需要哪些验证，或下一步该做什么。不要用“令人深思”“太震撼了”等无信息感叹代替结论。
